# AIOps Control Lab 面试讲解指南

## 一分钟介绍

这个项目解决的是“告警有了，但排障上下文分散”的问题。我搭建了一个 Nginx、FastAPI、Redis 三层实验环境，可以安全地停止 Redis。平台不是直接相信预设数据，而是实际访问 API 健康端点；确认出现 503 后创建 Incident，整理探测证据并调用大模型。模型只生成只读建议，真正的恢复操作必须经过人工审批，最后同时检查 Redis 容器和 API 依赖健康，验证通过后才关闭事件。

## 演示顺序

1. 打开演练中心，确认当前使用云模型还是规则降级。
2. 点击“开始演练”，说明故障目标和健康探针都是服务端白名单。
3. 展示 API 返回 503、延迟和发生时间。
4. 展示结构化诊断、修复计划和内容哈希。
5. 批准恢复，展示容器动作和 API 返回 200 的复检结果。
6. 打开 Incident 与审计页面，说明事件状态和幂等执行记录。

## 三个值得讲的技术点

### 真实观测而不是预设结果

场景目录只保存基线和预期根因。Redis 停止后，控制面必须从固定 `/healthz` 地址得到失败结果，才会建立事件；如果探测仍然健康，系统会清理故障并返回错误。

### AI 与执行权限隔离

模型只读取经过筛选的证据，不能生成任意 Shell。执行端只认识有限动作类型，计划内容在审批前计算哈希，审批后被修改会拒绝执行。

### 恢复不等于命令返回成功

重启容器成功只代表动作完成。系统还要重新访问 API 健康端点，只有下游依赖真正恢复才关闭 Incident，否则保留失败状态交给人工处理。

## 常见追问

**为什么用 Redis？**  它是实验 API 的真实下游依赖。停止后 API 进程还活着，但业务健康检查失败，适合展示依赖故障传播。

**为什么不让 AI 自动修复？**  模型输出不稳定，也不了解完整变更上下文。项目把诊断和执行分开，通过白名单、人工审批、计划哈希和复检降低风险。

**没有模型密钥还能运行吗？**  可以。诊断服务会使用确定性规则返回保守建议，并在界面明确标记降级状态。

**这是不是生产系统？**  不是。它是可重复的单机实验平台，重点验证故障闭环和安全边界；生产化还需要身份系统、消息队列、高可用和变更治理。

**你最熟悉哪部分？**  优先讲实验 API、健康探针、Incident 状态流转、审批执行和恢复验证，不主动展开所有算法与插件模块。
